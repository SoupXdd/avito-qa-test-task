# Задание 2.1. Тест-кейсы API

Стенд — `https://qa-internship.avito.com`. Для каждого прогона использовать свои данные
ID продавца взять из `POST /api/1/register`, токен из `POST /api/1/autorize`. Для защищенных запросов передать `Authorization: Bearer <accessToken>`, для JSON — `Content-Type: application/json`

## Регистрация и вход

### 1. API-01

**2. Название:** Регистрация нового пользователя

**3. Предусловия:** Есть новый `username` и валидный `password`

**4. Шаги:**

1. Отправить `POST /api/1/register` с полями `username` и `password` из предусловий

**5. Ожидаемый результат:** HTTP `201`. В ответе есть числовой `id`, а `username` совпадает с отправленным

### 1. API-02

**2. Название:** Повторная регистрация с тем же логином

**3. Предусловия:** Есть пользователь с паролем A. Для повтора взять другой валидный пароль B. В Bruno сделать копию запроса без скрипта, который меняет логин

**4. Шаги:**

1. Отправить `POST /api/1/register` с существующим `username` и паролем B
2. Вызвать `POST /api/1/autorize` с тем же логином и паролем A
3. Повторить вход с паролем B

**5. Ожидаемый результат:**

1. `409`
2. `200` и непустой `accessToken`
3. `401` без `accessToken`

### 1. API-03

**2. Название:** Регистрация с отсутствующим или пустым полем

**3. Предусловия:** Для каждого варианта подготовлены новый логин и валидный пароль

**4. Шаги:**

1. Для каждого варианта отправить отдельный `POST /api/1/register`. Менять только одно поле, второе оставить валидным. Вариант 1 — удалить поле `username`. Вариант 2 — удалить поле `password`. Вариант 3 — передать `username: ""`. Вариант 4 — передать `password: ""`

**5. Ожидаемый результат:** Каждый запрос возвращает `400`. В ответе нет данных созданного пользователя

### 1. API-04

**2. Название:** Вход с правильным логином и паролем

**3. Предусловия:** Зарегистрирован новый продавец. Известны его логин, пароль и `id`. Объявлений у него еще нет

**4. Шаги:**

1. Отправить `POST /api/1/autorize` с логином и паролем продавца
2. Вызвать `GET /api/1/{sellerID}/item` с `id` продавца из регистрации и токеном из шага 1

**5. Ожидаемый результат:**

1. `200`, непустой строковый `accessToken` и `tokenType: "Bearer"`
2. `200` и пустой массив `[]`

### 1. API-05

**2. Название:** Вход с неверными учетными данными

**3. Предусловия:** Есть зарегистрированный пользователь, другой валидный пароль и новый логин

**4. Шаги:**

1. Отправить `POST /api/1/autorize` отдельно для каждого набора данных. Вариант 1 — зарегистрированный логин и другой валидный пароль. Вариант 2 — незарегистрированный логин и пароль допустимого формата

**5. Ожидаемый результат:** Оба запроса возвращают `401`. Поля `accessToken` в ответах нет

### 1. API-06

**2. Название:** Вход без одного из обязательных полей

**3. Предусловия:** Известны валидные логин и пароль тестового пользователя

**4. Шаги:**

1. Отправить два отдельных `POST /api/1/autorize`. Вариант 1 — только `password`. Вариант 2 — только `username`

**5. Ожидаемый результат:** Оба запроса возвращают `400` без `accessToken`

## Доступ к API

### 1. API-07

**2. Название:** Защищенные ручки отклоняют запрос без авторизации

**3. Предусловия:** Для каждого запроса нужен свой продавец с токеном и объявлением. Для POST взять тело из [API-09](#1-api-09) с новым названием

**4. Шаги:**

1. Отправить запрос из списка с валидными данными и без заголовка `Authorization`
2. После POST запросить список с токеном владельца. После DELETE прочитать по тому же UUID с токеном владельца
3. Повторить с новыми данными для каждого варианта

**5. Ожидаемый результат:** Каждый запрос из списка возвращает `401`

1. `POST /api/1/item` с новым названием — В авторизованном списке продавца нет объявления с этим названием
2. `GET /api/1/item/{id}` — Ответ не содержит данных объявления
3. `GET /api/1/{sellerID}/item` — Ответ не содержит список объявлений
4. `GET /api/1/statistic/{id}` — Ответ не содержит статистику
5. `GET /api/2/statistic/{id}` — Ответ не содержит статистику
6. `DELETE /api/2/item/{id}` — Авторизованное чтение по этому UUID возвращает `200` и ту же запись

**6. Очистка:** Удалить объявление из предусловия и новую запись, если она неожиданно появилась

### 1. API-08

**2. Название:** Защищенные ручки отклоняют невалидный Bearer-токен

**3. Предусловия:** Для каждой ручки из API-07 нужен свой продавец с валидным токеном и объявлением. Для POST взять тело из [API-09](#1-api-09) с новым названием

**4. Шаги:**

1. Отправить каждый запрос из списка API-07 с заголовком `Authorization: Bearer not-a-token`
2. После POST запросить список с токеном владельца. После DELETE прочитать объявление по тому же UUID с этим токеном

**5. Ожидаемый результат:** Все шесть запросов дают `401`. Чтение не возвращает защищенные данные. После попытки создания новая запись отсутствует, после попытки удаления исходное объявление читается

**6. Очистка:** Удалить созданные для прогона объявления, включая лишнюю запись, если она появилась

## Объявления

### 1. API-09

**2. Название:** Создание и чтение объявления по UUID

**3. Предусловия:** Есть авторизованный продавец. Подготовить JSON с его `sellerID`, уникальным `name` вида `QA стол <суффикс>`, `price: 9900` и `statistics: {"likes": 21, "viewCount": 11, "contacts": 43}`

**4. Шаги:**

1. Отправить `POST /api/1/item` с этим телом и токеном продавца
2. Вызвать `GET /api/1/item/{id}` с тем же токеном и UUID из строки `status` шага 1

**5. Ожидаемый результат:**

1. `200`, в строке `status` есть корректный UUID
2. `200`, массив из одной записи. `id` совпадает с UUID, `sellerId` — с отправленным `sellerID`, `name` — с отправленным названием. В ответе `price=9900`, `likes=21`, `viewCount=11` и `contacts=43`

**6. Очистка:** Удалить объявление через `DELETE /api/2/item/{id}` с токеном владельца

### 1. API-10

**2. Название:** Два одинаковых запроса создают две отдельные записи

**3. Предусловия:** Есть авторизованный продавец и тело создания из [API-09](#1-api-09) с ID этого продавца и новым названием

**4. Шаги:**

1. Отправить это тело в `POST /api/1/item` и записать UUID из `status`
2. Повторить запрос с тем же токеном и тем же телом. Записать второй UUID
3. Запросить каждое объявление отдельно через `GET /api/1/item/{id}`

**5. Ожидаемый результат:**

Шаги 1 и 2: `200` в обоих ответах, UUID корректны и различаются

Шаг 3: Оба GET возвращают `200` и по одной записи с запрошенным UUID. Продавец, название, цена и счетчики совпадают с отправленными

**6. Очистка:** Удалить обе записи по их UUID

### 1. API-11

**2. Название:** Создание с `sellerID` другого продавца

**3. Предусловия:** Есть два своих продавца, A и B. У каждого есть ID и токен. Для POST взять тело из [API-09](#1-api-09) с новым названием

**4. Шаги:**

1. Отправить `POST /api/1/item` с токеном A и ID продавца B в поле `sellerID`
2. Запросить `GET /api/1/{sellerID}/item` для A и B, каждый раз с токеном владельца списка

**5. Ожидаемый результат:** Создание отклонено с клиентской ошибкой входных данных или доступа. Оба списка возвращают `200`, нового объявления нет ни в одном. Коллекция перечисляет `400` и `401` без привязки к этому случаю. Успешный ответ или `5xx` означает провал кейса

**6. Очистка:** Если запись появилась, удалить ее по UUID с токеном своего продавца, которому она была добавлена

### 1. API-12

**2. Название:** `X-UserId` не меняет владельца объявления

**3. Предусловия:** Есть два своих авторизованных продавца A и B с известными ID. Подготовлено тело из [API-09](#1-api-09) с ID продавца A и новым названием

**4. Шаги:**

1. Отправить `POST /api/1/item` с токеном и `sellerID` продавца A. Добавить заголовок `X-UserId` с ID продавца B
2. При успехе извлечь UUID, прочитать объявление с токеном A и проверить `sellerId`
3. При отказе запросить списки A и B, каждый с токеном владельца, и проверить наличие отправленного названия

**5. Ожидаемый результат:** При `200` созданное объявление читается и принадлежит A. При отказе возвращается клиентская ошибка входных данных или доступа, записи нет в обоих списках. `5xx` означает провал кейса

**6. Очистка:** Удалить созданную запись, если она появилась

### 1. API-13

**2. Название:** Создание с невалидным JSON или `sellerID`

**3. Предусловия:** Для каждого варианта есть авторизованный продавец без объявлений и тело создания из [API-09](#1-api-09)

2. После каждого запроса вызвать `GET /api/1/{sellerID}/item` с настоящими ID и токеном продавца из предусловий

**5. Ожидаемый результат:** Создание отклонено с ошибкой запроса. Список возвращает `200` и `[]`

**6. Очистка:** Если запрос неожиданно создал запись, удалить ее по UUID

**7. Допущение:** Для этих трех вариантов ожидаем `400`. В коллекции есть этот код, но не указано, когда он возвращается

**2. Название:** Список продавца с нулем, одним и двумя объявлениями

**4. Шаги:**

1. `[]`
2. Ровно одна запись с первым UUID A
3. Ровно две записи, оба UUID A встречаются по одному разу в любом порядке

**6. Очистка:** Удалить оба объявления A и объявление B с токенами их владельцев

## Удаление

### 1. API-21

**2. Название:** Удаление одного из двух объявлений

**3. Предусловия:** Есть авторизованный продавец с двумя объявлениями A и B. Известны оба UUID. Чтение A возвращает `200`, в списке есть обе записи

**4. Шаги:**

1. Удалить A через `DELETE /api/2/item/{id}`
2. Отдельно запросить A и B через `GET /api/1/item/{id}`
3. Запросить список продавца через `GET /api/1/{sellerID}/item`
4. Запросить статистику A через `GET /api/1/statistic/{id}` и `GET /api/2/statistic/{id}`

**5. Ожидаемый результат:**

1. `200`
2. Для A — `404`, для B — `200` и запись с UUID B
3. `200`, в списке только B
4. Обе версии возвращают `404`

**6. Очистка:** Удалить B. Если A осталась доступна, удалить и ее

### 1. API-22

**2. Название:** Удаление отсутствующего объявления

**5. Ожидаемый результат:** Оба DELETE и оба GET возвращают `404`. В ответах GET нет данных объявления
