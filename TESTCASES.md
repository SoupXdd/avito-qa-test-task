# Задание 2.1. Тест-кейсы API

Стенд — `https://qa-internship.avito.com`. Для каждого прогона использовать свои данные
ID продавца взять из `POST /api/1/register`, токен из `POST /api/1/autorize`. Для защищенных запросов передать `Authorization: Bearer <accessToken>`, для JSON — `Content-Type: application/json`

## Регистрация и вход

### API-01
- **Название:** Регистрация нового пользователя
- **Предусловия:** Есть новый `username` и валидный `password`

**Шаги:**

1. Отправить `POST /api/1/register` с полями `username` и `password` из предусловий

- **Ожидаемый результат:** HTTP `201`. В ответе есть числовой `id`, а `username` совпадает с отправленным

### API-02
- **Название:** Повторная регистрация с тем же логином
- **Предусловия:** Есть пользователь с паролем A. Для повтора взять другой валидный пароль B. В Bruno сделать копию запроса без скрипта, который меняет логин

**Шаги:**

1. Отправить `POST /api/1/register` с существующим `username` и паролем B
2. Вызвать `POST /api/1/autorize` с тем же логином и паролем A
3. Повторить вход с паролем B

- **Ожидаемый результат:**
  - Шаг 1: `409`
  - Шаг 2: `200` и непустой `accessToken`
  - Шаг 3: `401` без `accessToken`

### API-03
- **Название:** Регистрация с отсутствующим или пустым полем
- **Предусловия:** Для каждого варианта подготовлены новый логин и валидный пароль

**Шаги:**

1. Для каждого варианта отправить отдельный `POST /api/1/register`. Менять только одно поле, второе оставить валидным
   - A — удалить поле `username`
   - B — удалить поле `password`
   - C — передать `username: ""`
   - D — передать `password: ""`

- **Ожидаемый результат:** Каждый запрос возвращает `400`. В ответе нет данных созданного пользователя

### API-04
- **Название:** Вход с правильным логином и паролем
- **Предусловия:** Зарегистрирован новый продавец. Известны его логин, пароль и `id`. Объявлений у него еще нет

**Шаги:**

1. Отправить `POST /api/1/autorize` с логином и паролем продавца
2. Вызвать `GET /api/1/{sellerID}/item` с `id` продавца из регистрации и токеном из шага 1

- **Ожидаемый результат:**
  - Шаг 1: `200`, непустой строковый `accessToken` и `tokenType: "Bearer"`
  - Шаг 2: `200` и пустой массив `[]`

### API-05
- **Название:** Вход с неверными учетными данными
- **Предусловия:** Есть зарегистрированный пользователь, другой валидный пароль и новый логин

**Шаги:**

1. Отправить `POST /api/1/autorize` отдельно для каждого набора данных
   - A — зарегистрированный логин и другой валидный пароль
   - B — незарегистрированный логин и пароль допустимого формата

- **Ожидаемый результат:** Оба запроса возвращают `401`. Поля `accessToken` в ответах нет

### API-06
- **Название:** Вход без одного из обязательных полей
- **Предусловия:** Известны валидные логин и пароль тестового пользователя

**Шаги:**

1. Отправить два отдельных `POST /api/1/autorize`
   - A — только `password`
   - B — только `username`

- **Ожидаемый результат:** Оба запроса возвращают `400` без `accessToken`

## Доступ к API

### API-07
- **Название:** Защищенные ручки отклоняют запрос без авторизации
- **Предусловия:** Для каждого запроса нужен свой продавец с токеном и объявлением. Для POST взять тело из [API-09](#api-09) с новым названием

**Шаги:**

1. Отправить запрос из списка с валидными данными и без заголовка `Authorization`
2. После POST запросить список с токеном владельца. После DELETE прочитать по тому же UUID с токеном владельца
3. Повторить с новыми данными для каждого варианта

- **Ожидаемый результат:** Каждый запрос из списка возвращает `401`
  - `POST /api/1/item` с новым названием — В авторизованном списке продавца нет объявления с этим названием
  - `GET /api/1/item/{id}` — Ответ не содержит данных объявления
  - `GET /api/1/{sellerID}/item` — Ответ не содержит список объявлений
  - `GET /api/1/statistic/{id}` — Ответ не содержит статистику
  - `GET /api/2/statistic/{id}` — Ответ не содержит статистику
  - `DELETE /api/2/item/{id}` — Авторизованное чтение по этому UUID возвращает `200` и ту же запись
- **Очистка:** Удалить объявление из предусловия и новую запись, если она неожиданно появилась

### API-08
- **Название:** Защищенные ручки отклоняют невалидный Bearer-токен
- **Предусловия:** Для каждой ручки из API-07 нужен свой продавец с валидным токеном и объявлением. Для POST взять тело из [API-09](#api-09) с новым названием

**Шаги:**

1. Отправить каждый запрос из списка API-07 с заголовком `Authorization: Bearer not-a-token`
2. После POST запросить список с токеном владельца. После DELETE прочитать объявление по тому же UUID с этим токеном

- **Ожидаемый результат:** Все шесть запросов дают `401`. Чтение не возвращает защищенные данные. После попытки создания новая запись отсутствует, после попытки удаления исходное объявление читается
- **Очистка:** Удалить созданные для прогона объявления, включая лишнюю запись, если она появилась

## Объявления

### API-09
- **Название:** Создание и чтение объявления по UUID
- **Предусловия:** Есть авторизованный продавец. Подготовить JSON с его `sellerID`, уникальным `name` вида `QA стол <суффикс>`, `price: 9900` и `statistics: {"likes": 21, "viewCount": 11, "contacts": 43}`

**Шаги:**

1. Отправить `POST /api/1/item` с этим телом и токеном продавца
2. Вызвать `GET /api/1/item/{id}` с тем же токеном и UUID из строки `status` шага 1

- **Ожидаемый результат:**
  - Шаг 1: `200`, в строке `status` есть корректный UUID
  - Шаг 2: `200`, массив из одной записи. `id` совпадает с UUID, `sellerId` — с отправленным `sellerID`, `name` — с отправленным названием. В ответе `price=9900`, `likes=21`, `viewCount=11` и `contacts=43`
- **Очистка:** Удалить объявление через `DELETE /api/2/item/{id}` с токеном владельца

### API-10
- **Название:** Два одинаковых запроса создают две отдельные записи
- **Предусловия:** Есть авторизованный продавец и тело создания из [API-09](#api-09) с ID этого продавца и новым названием

**Шаги:**

1. Отправить это тело в `POST /api/1/item` и записать UUID из `status`
2. Повторить запрос с тем же токеном и тем же телом. Записать второй UUID
3. Запросить каждое объявление отдельно через `GET /api/1/item/{id}`

- **Ожидаемый результат:**
  - Шаги 1 и 2: `200` в обоих ответах, UUID корректны и различаются
  - Шаг 3: Оба GET возвращают `200` и по одной записи с запрошенным UUID. Продавец, название, цена и счетчики совпадают с отправленными
- **Очистка:** Удалить обе записи по их UUID

### API-11
- **Название:** Создание с `sellerID` другого продавца
- **Предусловия:** Есть два своих продавца, A и B. У каждого есть ID и токен. Для POST взять тело из [API-09](#api-09) с новым названием

**Шаги:**

1. Отправить `POST /api/1/item` с токеном A и ID продавца B в поле `sellerID`
2. Запросить `GET /api/1/{sellerID}/item` для A и B, каждый раз с токеном владельца списка

- **Ожидаемый результат:** Создание отклонено с клиентской ошибкой входных данных или доступа. Оба списка возвращают `200`, нового объявления нет ни в одном. Коллекция перечисляет `400` и `401` без привязки к этому случаю. Успешный ответ или `5xx` означает провал кейса
- **Очистка:** Если запись появилась, удалить ее по UUID с токеном своего продавца, которому она была добавлена

### API-12
- **Название:** `X-UserId` не меняет владельца объявления
- **Предусловия:** Есть два своих авторизованных продавца A и B с известными ID. Подготовлено тело из [API-09](#api-09) с ID продавца A и новым названием

**Шаги:**

1. Отправить `POST /api/1/item` с токеном и `sellerID` продавца A. Добавить заголовок `X-UserId` с ID продавца B
2. При успехе извлечь UUID, прочитать объявление с токеном A и проверить `sellerId`
3. При отказе запросить списки A и B, каждый с токеном владельца, и проверить наличие отправленного названия

- **Ожидаемый результат:** При `200` созданное объявление читается и принадлежит A. При отказе возвращается клиентская ошибка входных данных или доступа, записи нет в обоих списках. `5xx` означает провал кейса
- **Очистка:** Удалить созданную запись, если она появилась

### API-13
- **Название:** Создание с невалидным JSON или `sellerID`
- **Предусловия:** Для каждого варианта есть авторизованный продавец без объявлений и тело создания из [API-09](#api-09)

**Шаги:**

1. Для каждого варианта отправить отдельный `POST /api/1/item`
   - A — убрать последнюю закрывающую фигурную скобку JSON
   - B — удалить поле `sellerID`
   - C — передать `sellerID: {}`
2. После каждого запроса вызвать `GET /api/1/{sellerID}/item` с настоящими ID и токеном продавца из предусловий

- **Ожидаемый результат:** Создание отклонено с ошибкой запроса. Список возвращает `200` и `[]`
- **Допущение:** Для этих трех вариантов ожидаем `400`. В коллекции есть этот код, но не указано, когда он возвращается
- **Очистка:** Если запрос неожиданно создал запись, удалить ее по UUID

### API-16
- **Название:** Список продавца с нулем, одним и двумя объявлениями
- **Предусловия:** Зарегистрированы и авторизованы продавцы A и B. У A нет объявлений. У B создано одно объявление с известным UUID

**Шаги:**

1. С токеном A запросить `GET /api/1/{sellerID}/item` для A
2. Создать первое объявление A через `POST /api/1/item` с телом из [API-09](#api-09). Сохранить UUID из `status` и повторить GET списка
3. Создать второе объявление A с новым названием. Сохранить второй UUID и повторить GET списка

- **Ожидаемый результат:** Каждый запрос возвращает `200`. UUID продавца B не появляется ни в одном списке
  - Шаг 1: `[]`
  - Шаг 2: Ровно одна запись с первым UUID A
  - Шаг 3: Ровно две записи, оба UUID A встречаются по одному разу в любом порядке
- **Очистка:** Удалить оба объявления A и объявление B с токенами их владельцев

## Удаление

### API-21
- **Название:** Удаление одного из двух объявлений
- **Предусловия:** Есть авторизованный продавец с двумя объявлениями A и B. Известны оба UUID. Чтение A возвращает `200`, в списке есть обе записи

**Шаги:**

1. Удалить A через `DELETE /api/2/item/{id}`
2. Отдельно запросить A и B через `GET /api/1/item/{id}`
3. Запросить список продавца через `GET /api/1/{sellerID}/item`
4. Запросить статистику A через `GET /api/1/statistic/{id}` и `GET /api/2/statistic/{id}`

- **Ожидаемый результат:**
  - Шаг 1: `200`
  - Шаг 2: Для A — `404`, для B — `200` и запись с UUID B
  - Шаг 3: `200`, в списке только B
  - Шаг 4: Обе версии возвращают `404`
- **Очистка:** Удалить B. Если A осталась доступна, удалить и ее

### API-22
- **Название:** Удаление отсутствующего объявления
- **Предусловия:** Есть авторизованный продавец. Для первого варианта создана и успешно удалена его запись, UUID сохранен. Для второго сгенерирован новый UUID без создания записи

**Шаги:**

1. Отправить `DELETE /api/2/item/{id}` для выбранного варианта
   - A — UUID уже удаленной записи
   - B — новый UUID, по которому запись не создавалась
2. Запросить тот же UUID через `GET /api/1/item/{id}`

- **Ожидаемый результат:** Оба DELETE и оба GET возвращают `404`. В ответах GET нет данных объявления

### API-23

- **Предусловия:** Есть авторизованный продавец

**Шаги:**
